# S3.3 - Atomic synthetic ingestion and quarantine

Base S3.2 GREEN ec83cc3a3b38f0bb19dc5f8eb912c278dc2a7e42, PR #66, issue #65. No real network,
training, scoring, schema changes, worker scheduler or UI wiring.
Files ingestion/pipeline.py, tests/v4/test_ingestion_pipeline.py,

Interface ingest_batch(conn, policy, url, transport, *, job_id,
started_at, observed_at, available_at, ended_at, sleep)->IngestReport
(frozen fields status, reason, inserted, replayed, snapshot_id).
Clocks are explicit synthetic caller inputs, normalized UTC. Validate
started <= observed <= ended and observed <= known available <= ended.
Require idle writer FK/recursive triggers and verified exact v3 schema.
Invalid invocation, unknown schema or reused terminal job ID raises
ValueError before transport and writes; preserve caller transaction.
Single trusted writer assumption; no OS lease/scheduler yet.
Job ID synthetic, unique per invocation, not a replay token; same job
ID cannot fetch twice once terminal receipt exists. New ID required
for restart/re-observation. Job attempt=1 is invocation receipt, not
internal adapter retry count. No transaction across fetch or sleep.
Check registered synthetic LOCKED source and adapter policy before
transport. Denied scope -> BLOCKED/FETCH_BLOCKED terminal job, no
quarantine (unknown source cannot satisfy FK); never fetch or sleep.
Fetch success -> BEGIN IMMEDIATE; recheck schema/source/job ID,
parse receipt in transaction, insert snapshot, then all typed rows
and SUCCEEDED job receipt atomically. Empty batch allowed.
Data error -> rollback all data and then separate transaction with
FAILED job plus one quality issue for known source, deterministic
issue ID derived from job ID. Fixed sanitized codes:
PARSE_REJECTED, REVISION_CONFLICT, FETCH_TRANSIENT_EXHAUSTED,
FETCH_PERMANENT, INVALID_PAYLOAD. No raw payloads or exception messages.
Unexpected transport/SQLite/system errors propagate; rollback if needed,
do not fabricate terminal receipt or classify infrastructure failure as
data quality. Failed receipt persistence also propagates.

Re-observation: compare existing row by (match_id,source_id,revision),
including stable revision ID, exact normalized provider fields and
canonical participant/winner values. If exact entire record -> replay.
If identical semantic fields and strictly later observed_at -> replay
keeping original snapshot/availability/observed_at; persist new snapshot
but no extra revision row. Later snapshot has no row-level replay link
in current schema; no claim complete observation history. Earlier
observation, same observation with different snapshot/availability,
ID mismatch, or changed provider fields without new revision -> conflict.
Never backdate or revise earlier availability. New revision is append.
Identity mismatch/invalid input -> reject whole batch. No silent remap.
All writes using S2 typed APIs; no raw UPDATE/DELETE. Deterministic IDs
from parser. Do not modify S2 schema or previous tests.
